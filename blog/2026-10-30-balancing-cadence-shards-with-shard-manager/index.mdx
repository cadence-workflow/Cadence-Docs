<Essay>

For the past year the Cadence team has worked on Shard Manager, a new
standalone, general-purpose sharding service (earlier covered in [1 Day, 2 Engineers, 6 Lines of
Code](../2026-04-20-shard-manager-incident/2026-04-20-shard-manager-incident.mdx)).
We have now onboarded Cadence's Matching service, which routes workflow and
activity tasks to workers, to Shard Manager across all of Uber. With near-optimal
load-aware placement, CPU utilization on the hottest Matching host dropped by
about a third.
To use it in your own service, start with the [Shard Manager
documentation](/docs/shard-manager).

<BeforeAfterPlacement />

## Why we built Shard Manager

Cadence distributes workflows across its hosts, grouping them into shards, and
distributes the shards evenly using [consistent
hashing](https://en.wikipedia.org/wiki/Consistent_hashing), via the long
deprecated [ringpop](https://github.com/uber/ringpop-go) library. So long as
each host knows the full set of hosts, it's able to determine exactly what it
should be working on and how to route requests to peers.

Both this distribution and coordination became recurring problems:

- **Hot sharding.** Not all shards are equal, and we constantly saw massive
  skews in CPU utilization. Evenly distributing the shards doesn't evenly
  distribute the work.
- **Distributed membership.** Gossip protocols eventually converge, but
  discrepancies cause conflicts, slow down the system, and are challenging to
  debug. Each host is individually responsible for assignment and there's no
  authoritative answer.
- **Little control.** The only way to change the distribution is changing the
  membership, adding or removing hosts. A host that is degraded but still up
  keeps all its shards.

We saw this when a Matching host ran hot and our auto-scaler added more hosts.
Each new host took over a random set of shards, so the hot shards could still
end up together on one host. **Adding capacity didn't fix the hotspot.**

We realized we could no longer proceed without a central service, and we
decided to build Shard Manager. It owns shard placement, balances shards by
their observed load, gives one authoritative answer to who owns a shard, and
lets operators drain a host or stop a single shard.

## Load balancing and results in Uber's production environments

In Matching, the shards are task lists, the queues that workers poll for tasks,
and each one lives on exactly one host.
Below we see data over a month in one of Uber's production Matching clusters.
The period covers the time before and after the onboarding.

We see that the average barely moves, as total traffic stays about the same.
However, the spread decreases, leading to much better utilization. Under the

### How close is this to the best possible?

To check how good the placement is, we took a snapshot of the load of every
shard in each environment we've rolled out to. We then asked a constraint solver
for the best possible placement of exactly those shards on exactly those hosts.

We measure balance as load spread, the standard deviation of host load divided
by the average host load. At 0, every host carries the same load. Across
environments, Shard Manager's spread was within 5% of the solver's in 23 of 24
snapshots, and within 1% in 14.

The logic underneath the balancing is explained [further down](#how-the-load-balancing-works).

## Operations with smctl

Because all assignments are now centrally managed, operators can inspect shard
ownership, drain a host, or isolate a shard with a single command using the
`smctl` CLI.

We can now answer questions such as:

**Who owns this shard?** With the hash ring, the answer depended on
which host you asked. Each service instance calculated shard ownership from its
own view of cluster membership. Those views could temporarily differ, producing
conflicting answers. Now, Shard Manager lets you fetch the owner directly:

```console
$ smctl --namespace cadence-matching shard inspect --shard-key orders-tasklist
{
  "Owner": "6c1f0e2a-…",
  …
}
```

**A host is misbehaving.** Drain it, and its shards move to the other hosts:

```console
$ smctl --namespace cadence-matching executor drain \
    --hostname matching-host-3 --reason "debugging high latency"
Host "matching-host-3" currently holds 212 shard(s):
  executor 6c1f0e2a-…: 212 shard(s)
Proceed with draining? [y/N]: y
```

**A shard keeps crashing its host.** Moving it just crashes the next host, and
then the next, until the whole cluster is down. Instead we drain the shard so it
stops being assigned while we investigate.

```console
$ smctl --namespace cadence-matching shard drain --shard-key orders-tasklist
{
  "Namespace": "cadence-matching",
  "ShardKeys": [
    "orders-tasklist"
  ]
}
```

## How it works

### Architecture

The results above are possible due to the centralized architecture of the Shard
Manager. We onboarded Matching first. Integrating it is much simpler than
History, the Cadence service that manages workflow state and execution, and the
cost of moving a task list between hosts is low. When we bring History onto
Shard Manager next, we expect a larger effect on CPU utilization, and with it
the ability to handle the same load with fewer instances. Below we see an
architecture diagram of the full system with the Matching integration.

<Figure
  title="How requests reach a Matching host"
  subtitle="Matching hosts heartbeat to Shard Manager, which assigns shards and pushes the routing map to Frontend."
>
  <ArchitectureFlow />
</Figure>

The system consists of three roles:

- **The Shard Manager.** The central service, backed by etcd, is responsible for
  deciding placements and communicating these placements to the rest of the
  system. The instances of Shard Manager elect a leader for each namespace, which
  is responsible for load balancing and changing assignments when hosts
  join and leave.
- **The Executors.** Cadence has two sharded services, Matching and History.
  The executors are the instances of the service responsible for processing
  the shards, in this case Matching. The Matching instances heartbeat to the Shard Manager, which allows
  the Shard Manager to track liveness. Additionally, the heartbeats include load
  information for all shards the executor owns. For Matching, the load measure is
  the number of tasks the task list processes.
- **The Spectators.** These are the services that need to know who owns a shard.
  In the diagram we see Cadence Frontend in the role of spectator, as it routes
  each request to the Matching host that owns the task list. The spectators
  establish a gRPC stream to the Shard Manager, which then pushes new shard
  assignments to the spectators as the assignments change.

:::tip[A service can play both roles]

The same service can be both spectator and executor. The receiving
instance can then forward the requests to the correct owner, allowing the
callers of the service to not know about the sharding of the service.

:::

For more information, see the [Shard Manager
architecture](/docs/shard-manager/architecture).

### How the load balancing works

With the executors reporting the load of each shard they own, we can do
load-aware balancing. Below is an example with six hosts. It starts from a hash
ring's placement, where every host has the same number of shards. To keep it
easy to follow, each step is a single move.

<Figure
  title="Shard Manager load balancing six hosts"
  subtitle="Step through it with Next, or the arrow keys. A shard turns blue when it moves and fades back to grey as its cooldown runs out."
>
  <ShardManagerDemo />
</Figure>

The Shard Manager smooths the loads so small variations don't trigger moves.
Every few seconds it looks for an imbalance:

- It compares each host with the average host using hysteresis bands (upper
  and lower load thresholds). A host above the upper band is too hot, and a
  host below the lower band has room to take more load. Anything in between is
  left alone.
- Each cycle moves a small batch of shards, by default up to 1% of all shards.
  Each move goes from a hot host to the coldest one, picking the shard that
  brings the two closest together, excluding shards that would make the cold
  host hot.
- Shards that have recently moved have to cool down before they can be moved
  again, which prevents thrashing.

:::note[Hysteresis bands]

Hosts aren't perfectly balanced when we stop, and that's on purpose. Every
move has a cost, and past that point more moves would only churn shards
between hosts.

:::

## Future work

- **History.** Matching is the first Cadence service on Shard Manager. History
  will be onboarded next. We expect a larger CPU saving there, so the same load
  can run on fewer instances.
- **Make etcd optional.** Shard Manager stores its state in etcd today. We plan
  to remove that dependency, so Shard Manager will be able to run completely
  in memory.
- **Beyond Cadence.** Shard Manager is a generic service, not specific to
  Cadence. Any service that needs to shard its work can use it. The [service integration
  guide](/docs/shard-manager/integration) shows how, and we'd love to hear from
  teams who want to use it.
